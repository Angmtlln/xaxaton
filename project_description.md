# Описание проекта. Промежуточная версия

**Проект.** ИИ-агент для проверки контрагента по ИНН.
**Кейсодатель.** Альфа-Банк, Денис Анастасьев.
**Версия.** Промежуточная, от 03.09.2026. Финальная сдача — 07.09.2026.

---

## 1. Аннотация

Мы делаем агента, который по одному ИНН собирает отчёт банка о контрагенте и
отвечает предпринимателю на его собственный вопрос: «можно ли с ними работать
и не подведут ли они меня в ближайшее время».

Ключевое отличие от того, что уже есть в продукте банка: агент **не
пересчитывает оценку риска**, а выносит наверх факты, которые за этой оценкой
стоят и которые цветом светофора не отражены. Все числа считаются кодом из
сырых полей карточки, а не пересказываются моделью, и каждое утверждение
агента несёт ссылку на конкретное поле отчёта.

Сейчас работает сквозной прототип: PostgreSQL с загруженной выгрузкой из 100
карточек, детерминированный слой фактов, четыре доменных агента на Groq,
итоговая Summary-модель поверх них, REST API со Swagger и веб-интерфейс в
дизайне, подготовленном фронтендером команды.

## 2. Проблематика

Проверка контрагента в интернет-банке сегодня заканчивается PDF на 10–12
оценок. Разведочный анализ выгрузки и интервью с кейсодателем (02.09.2026)
показали три проблемы, которые и определили продукт.

**Итоговая метрика не покрывает часть жёстких фактов.** В выгрузке все 9
компаний с активной блокировкой счетов по постановлению ФНС помечены зелёным
светофором ЗСК, 8 из них — ещё и уровнем риска LOW. Единственная компания в
процедуре банкротства тоже числится LOW + GREEN. Пользователь, увидев зелёный
цвет, прекращает проверку и этих фактов не видит.

**Готовые текстовые формулировки отчёта расходятся с его же цифрами.** В 46
карточках из 100 отчёт хвалит компанию за «небольшое количество кодов ОКВЭД»,
тогда как кодов там от 10 до 29. Агент, который пересказывает прозу отчёта,
воспроизводит эту ошибку.

**Неполнота данных — это норма, а не краевой случай.** Финансовой отчётности
нет у 33 карточек из 100, коэффициентов — у 81, лицензий — у 91. Отчёт
визуально одинаков и для заполненной, и для пустой карточки, поэтому
пользователь принимает неполные данные за полные.

Подробный разбор проблематики и полный список гипотез — в
[hypotheses.md](hypotheses.md).

## 3. Постановка задачи

Построить агента, который по ИНН из загруженного отчёта банка формирует
объяснимый вывод для предпринимателя малого бизнеса.

**Функциональные требования.**

1. Вход — один ИНН. Никаких файлов пользователь не загружает.
2. Источник истины — выгруженный отчёт банка. Внешние источники необязательны.
3. Оценки банка `riskLevel` и `zskRiskLevel` приводятся без изменений, свой
   скоринг не считается.
4. Каждое утверждение агента сопровождается ссылкой на поле входных данных.
5. При отсутствии данных агент обязан прямо сказать «невозможно оценить по
   этому критерию» и отдельно оговорить, что отсутствие записей не равно
   отсутствию факта.
6. Формулировки не категоричные: агент обращает внимание на факты, а не
   выносит приговор.
7. Итог — словесная группа рекомендации, а не числовой рейтинг.

**Нефункциональные требования.** Проход по одному ИНН — единицы секунд.
Модели — с бесплатного тарифа Groq. Карточка достигает 238 КБ (порядка 80 тыс.
токенов), поэтому подача сырого JSON в контекст исключена.

## 4. Техническое решение

### 4.1 Схема прохода

```
ИНН
 └─ карточка отчёта из PostgreSQL (последний снапшот по компании)
     └─ детерминированный слой: факты считаются кодом из сырых полей,
        раскладываются по 4 блокам, у каждого факта id и путь к полю
         ├─ агент «Кто это»                     openai/gpt-oss-20b
         ├─ агент «Надёжность и правовые риски» openai/gpt-oss-120b   параллельно
         ├─ агент «Финансовое состояние»        qwen/qwen3.8-27b
         └─ агент «Опыт и позитивные сигналы»   openai/gpt-oss-20b
             └─ Summary-LLM поверх четырёх резюме  openai/gpt-oss-120b
                 └─ guardrails + сверка ссылок + запись прогона в БД
                     └─ ответ API и экран отчёта
```

### 4.2 Принятые архитектурные решения

**Детерминированный слой фактов до модели.** Количество кодов ОКВЭД, суммы и
статусы исполнительных производств, роль в арбитраже, динамика выручки,
реестровые метки — всё считается кодом. Готовая проза отчёта
(`reputationalRisks[].name`) хранится и показывается пользователю, но не
является входом для выводов. Это решение одновременно закрывает три проблемы:
противоречия в исходных текстах, размер контекста и формат Mongo Extended JSON
(`$numberLong` строкой, `$date`, одно и то же поле то числом, то обёрткой).

**Четыре блока вместо семи.** Деление сделано по вопросам пользователя, а не по
разделам спецификации: «кто это», «есть ли повод не связываться», «в каком
состоянии бизнес», «есть ли подтверждённый опыт». Обоснование и раскладка
реальных атрибутов — в [blocks_summary_design.md](blocks_summary_design.md).

**Заземление ответов.** Каждый факт имеет идентификатор и `field_ref`. Модель
возвращает `fact_id`, сервис сверяет его с реестром фактов прогона. Ссылка на
несуществующий факт помечается `UNVERIFIED`, попадает в метрику ответа и в
таблицу `audit.run_statements`. Это и есть измеримый критерий «не выдумывает».

**Защитный слой поверх модели.** Вывод не может быть мягче фактов, посчитанных
кодом: при наличии жёсткого факта сигнал блока поднимается до `RISK`, итоговая
группа — до `STOP`, а сам факт принудительно добавляется в список наблюдений.
Все срабатывания показываются пользователю, а не прячутся.

**Разные модели на разные блоки.** Лимит бесплатного тарифа Groq считается
отдельно по каждой модели (8000 токенов в минуту), а четыре агента вместе весят
около 8 тыс. токенов промпта. На одной модели проход упирается в 429 и половина
блоков не отвечает. Блоки разведены по трём моделям, при 429 вызов уходит на
следующую модель из списка запасных, и только если заняты все — клиент ждёт
паузу, которую называет сам Groq. Для `gpt-oss` включён `reasoning_effort: low`:
ответ короче вчетверо и перестаёт обрываться на середине JSON.

**Отказ не роняет проход.** Если модель недоступна, блок собирается
детерминированным шаблоном по тем же фактам, прогон получает статус `PARTIAL`,
а на экране появляется предупреждение с текстом ошибки.

### 4.3 Стек

PostgreSQL 16, Python 3.11 + FastAPI (Swagger из коробки), psycopg 3, httpx,
модели Groq. Веб-интерфейс — статические страницы, раздаются тем же сервисом.
Оформление перенесено из прототипа фронтендера команды.

**API.** `POST /api/v1/checks` — полный проход по ИНН; `GET /api/v1/checks` и

`GET /api/v1/companies/{inn}/coverage` — паспорт полноты; `GET /health`.

## 6. Предварительные результаты

Все цифры ниже измерены на реальном прогоне, а не оценены.

**Загрузка данных.** 100 компаний, 100 снапшотов. Счётчики сходятся с сырым
JSON: 3873 исполнительных производства (из них 770 без раскрытой суммы), 2228
кодов ОКВЭД, 1643 репутационные метки, 343 проверки, 249 связанных компаний,
194 года финансовой отчётности. Повторный запуск загрузчика дублей не создаёт.

**Контрольный прогон по всей выборке.** 100 ИНН через API: 100 успешных
проходов, 0 ошибок, 1352 утверждения, из них 0 ссылок на несуществующие факты.
33 карточки получили по финансовому блоку сигнал `NO_DATA` и явное «оценить
невозможно» — ровно те 33, у которых финансовой отчётности нет.

**Проверка гипотез на базе.** Витрина расхождений по ОКВЭД даёт 46 карточек —
цифра из гипотезы H4 подтвердилась на независимом пересчёте в SQL. Витрина
«зелёный светофор при негативных метках» даёт 40 карточек, из них 8 — с
блокировкой счетов ФНС при уровне риска LOW.

**Живые модели.** Проверено на трёх контрагентах: все четыре блочных агента и
Summary-модель отвечают, статус `SUCCEEDED`, полный проход занимает около 5
секунд при 12–14 тыс. токенов промпта и 2,5–5 тыс. токенов ответа. Доля
утверждений со ссылкой на факт — от 96 до 100 %. В одном прогоне модель
сослалась на 3 несуществующих факта из 26 утверждений: механизм пометил их как
`UNVERIFIED` и показал в метрике, то есть детектор работает на живых данных.

**Тесты.** 22 теста, включая контрольную сверку вычисленных фактов с сырыми
полями по всем 100 карточкам, проверку наличия `field_ref` у каждого факта,
обработку ответа модели со ссылкой на несуществующий факт и переключение
модели при исчерпании лимита токенов.

## 7. Ограничения текущей версии

**Продуктовые.**

- Диалог с доуточнениями по отчёту (гипотеза S3) не реализован — только
  одноразовый проход.
- Сравнение нескольких контрагентов в одном сеансе (S4) не реализовано.
- Подбор контрагента по запросу (S8), веб-поиск (S9) и граф связей (S10)
  сознательно вынесены за скоуп промежуточной версии.
- Экспертная разметка утверждений не проведена, поэтому критерии успеха 1, 2, 5
  и 6 пока подтверждены только автоматической проверкой, но не человеком.

**Технические.**

- Данные статичны: снапшот из 100 карточек, обновления не приходят.
- Бесплатный тариф Groq ограничен 8000 токенами в минуту на модель. При частых
  прогонах подряд проход растягивается с 5 до 30–60 секунд из-за ожидания окна.
- Модели уровня 20B иногда ссылаются на несуществующий факт. Мы это ловим и
  показываем, но не устраняем полностью.
- Граф связей построить не на чем: внутри выборки найдено всего 2 связи между
  компаниями.

## 8. Открытые вопросы

**К кейсодателю.**

1. Сценарии приёмки — обещаны, ждём.
2. Клиентские исследования по гипотезам H1 (пользователь смотрит только
   итоговую метрику) и H6 (распределение числа проверок на клиента за квартал).
3. Подтверждение H3: показать 10 карточек «зелёный цвет при жёстких метках»,
   включая банкротство при LOW + GREEN, и получить подтверждение, что эти факты
   нужно выносить отдельно от цвета.
4. Подтверждение H4: показать список из 46 расхождений по ОКВЭД и уточнить, это
   дефект данных или мы неверно читаем поле.
5. Сверка трёх групп рекомендаций с формулировками эталонной аналитики.

**Внутренние.**

6. Две цифры из нашего же первичного анализа не сошлись с прямым пересчётом в
   базе: максимум кодов ОКВЭД указан как 27, по факту в выборке есть карточка
   со 121 кодом (внутри 46 противоречивых максимум — 29); карточек с нулевым
   покрытием по 9 блокам не 13, а 12. Методику подсчёта нужно перепроверить до
   финала, в материалах используем цифры, пересчитанные в базе.
7. Нужен ли платный тариф Groq на время демонстрации, чтобы исключить ожидание
   по лимиту токенов при прогонах подряд.

## 11. Как запустить

```bash
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env                  # вписать GROQ_API_KEY

docker compose up -d db               # или локальный PostgreSQL 16
python scripts/load_snapshot.py --create-schema --file ../contractors_audit.snapshot.json
uvicorn app.main:app --port 8000
```

Интерфейс — `http://localhost:8000/`, Swagger — `http://localhost:8000/docs`.
Без ключа модели сервис работает в детерминированном режиме: `LLM_MOCK=true`.
Подробности — в [backend/README.md](backend/README.md), обоснование схемы БД —
в [backend/docs/db_design.md](backend/docs/db_design.md).
