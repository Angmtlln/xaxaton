## Продукт и ценность

ИИ-аналитик помогает предпринимателю изучить контрагента, объясняет важные
наблюдения и ограничения данных, сравнивает компании и помогает подобрать
кандидатов под условия сотрудничества. Основной продукт — разговор с Master
Agent. Полный отчёт остаётся отдельной детализацией.

Пользователь не должен самостоятельно сводить большую карточку в вывод.
Агент объясняет факты за банковскими оценками, показывает расхождения и пробелы.
`riskLevel` и `zskRiskLevel` независимы и не пересчитываются. Общего собственного
рейтинга риска нет. Числа, идентификаторы, источники и графики формирует backend;
модель интерпретирует проверенные наблюдения.

Постановка, аудитория и критерии успеха: [PROJECT_CONTEXT](docs/PROJECT_CONTEXT.md).
Исторические продуктовые исследования: [product_materials](product_materials.md)
и [hypotheses](hypotheses.md); их цифры не являются новыми замерами текущего сервиса.

## Реализованные сценарии

| Возможность | Как пользоваться | Границы |
|---|---|---|
| Полная проверка | «Проверь контрагента 7805327192» | Компактная сводка и ответ аналитика; подробный отчёт отдельно |
| Контекстный диалог | «Почему?», «Объясни проще» | Использует сохранённый проверенный контекст, когда его достаточно |
| Узкие вопросы | «Что у них с финансами?» или вопрос о судах | Targeted tools без повторного полного pipeline |
| Сравнение | «Сравни 7805327192 и 4720028039» | 2–5 ИНН, единый ToolResult и отдельный контекст сравнения |
| Поиск и подбор | Описать деятельность, показатели или цель сотрудничества | По загруженным данным; подбор до 50 кандидатов и до 5 финалистов |
| Связи компаний | После проверки: «Построй граф связей» | Один шаг по доступной выборке; совпадение названий не доказывает связь |
| Новости | Запросить полную проверку | Отдельный внешний блок, без изменения внутренних фактов и банковских оценок |
| PDF | Экспортировать результат средствами чата | Подробнее в [PDF_EXPORT](docs/PDF_EXPORT.md) |

Desktop-интерфейс включает качественный профиль AI с пояснениями,
контекстные действия и статусы этапов обработки. Статусы передаются NDJSON;
это не потоковая выдача токенов Master. Мобильные доработки приостановлены.
Подробности: [CHAT_UI](docs/CHAT_UI.md), [подбор](docs/COUNTERPARTY_SELECTION.md),
[связи](docs/COMPANY_CONNECTIONS.md), [новости](docs/WEB_NEWS.md).

## Архитектура и данные

```text
Чат → API → Master Agent (LangChain create_agent / LangGraph)
    → разрешённые domain tools → repository → PostgreSQL
    → проверенные наблюдения → объяснение Master → backend hydration → UI
```

Выгрузка `contractors_audit.snapshot.json` импортируется в PostgreSQL.
Исходные JSON хранятся в `raw.report_documents.document`, нормализованные
карточки — в `core.*`, результаты проверок — в `audit.*`.
Офлайн-демо читает файл отдельно от рабочего пути БД.

Master по умолчанию настроен на `z-ai/glm-5.3-flash` через OpenRouter;
доменные агенты независимо используют Groq. Это настройки кода, а не
подтверждение доступности моделей или успешности последнего live-запроса.

Полная проверка в чате вызывает четыре доменных блока через
`run_check(include_summary=False)`, затем Master формирует ответ.
Legacy `/api/v1/checks` сохраняет отдельную Summary-модель и аудит.
Узкие финансовые/юридические вопросы и сравнение используют builders без
полных проверок каждой компании. Поиск и подбор имеют собственные ограничения.

Trusted context хранится отдельно от прозы диалога. Структурная валидация
действует постоянно; дополнительная LLM-проверка grounding и repair по
умолчанию выключена и включается через `AGENT_GROUNDING_DEBUG` для eval/debug.
Техническая валидность ответа не гарантирует правильность рассуждения.

## Проверенность и ограничения

- Данные — статичная демонстрационная выгрузка из 100 карточек; текущая
  наполненность запущенной БД зависит от загрузки. Обновления извне не подключены.
- Состояние диалога хранится в памяти одного процесса и теряется при перезапуске;
  сохранённый аудит проверок не заменяет постоянную историю чата.
- Есть банк [AGENT_EVALS](AGENT_EVALS.md) и [реальный eval harness](backend/evals/README.md).
  Исходные вопросы сохраняются дословно. Технический PASS отделяется от
  semantic acceptance; содержательные ошибки ещё остаются.
- Измерения задержек и провайдеров находятся в [CHAT_LATENCY](docs/CHAT_LATENCY.md),
  результаты поведения — в [индексе отчётов](docs/AI_INDEX.md). Это датированные
  прогоны, а не гарантия текущей скорости или качества.
- В наборе мало внутренних связей. Это ограничивает охват графа, но граф
  реализован; отсутствие связи в выборке не доказывает её отсутствие в мире.
- Нет универсального разрешения названий в ИНН, отдельного deal-risk инструмента,
  постоянной истории чата, промышленной интеграции банка и потокового текста.
- Недоступность LLM и недостаток данных приводят к ограниченному ответу/fallback;
  продукт не принимает юридические или финансовые решения за пользователя.

## Следующий шаг: MCP

Планируется реальный MCP-доступ к существующей PostgreSQL с демонстрационными
JSON: backend станет клиентом сервера чтения карточек и поиска. Дополнительная
LLM для этого не требуется. Расчёт фактов и запись аудита сохранят текущие границы.

MCP **пока не реализован**. Сначала нужен сквозной проход по ИНН, затем остальные
чтения, проверка ошибок и регрессии. Предварительно: 0,5–1 день на узкий проход,
1–3 рабочих дня суммарно на полный объём. Трактовка точного требования заказчика
остаётся рабочей гипотезой. [Архитектура и приёмка MCP](docs/MCP_DATA_ACCESS.md).

Приоритет дальнейшей работы — MCP, содержательная проверка ответов и
воспроизводимая desktop-демонстрация. Старый календарный план 04–06.09 не
используется как перечень ещё не реализованных функций.

## Запуск и демонстрация

Следовать [backend/README](backend/README.md): PostgreSQL, импорт выгрузки,
настройка OpenRouter/Groq, запуск API. Приложение открывается на
[localhost:8000](http://localhost:8000/), схема API — в
[Swagger](http://localhost:8000/docs).

Короткий сценарий: полная проверка → объяснение → узкий финансовый вопрос →
граф связей → отдельная проверка соседней компании → сравнение.
Сценарий связи двух ООО «ЛЗСО» и команда живого smoke описаны в
[COMPANY_CONNECTIONS](docs/COMPANY_CONNECTIONS.md). Живые вызовы расходуют токены;
их результат нужно проверить отдельно от unit-тестов.
