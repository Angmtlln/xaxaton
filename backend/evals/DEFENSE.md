# Проверка для защиты: defense-1

Новый benchmark расширяет существующий eval, не заменяя `AGENT_EVALS.md` и его
406 регрессионных реплик. Источник нового банка — `defense_bank.py`; вопросы и
обязательные части фиксируются до выполнения, JSON сверяется с source и snapshot.

150 сценариев: 100 самостоятельных, 30 многосоставных, 20 диалогов по 3–4 хода;
194 scored-реплики. Подготовительные реплики сохраняются отдельно и не увеличивают
знаменатель. 120 development и 30 holdout: holdout не входит в пилот и не должен
использоваться для настройки runtime/prompts. Повторы — попытки того же сценария.

## Данные и границы

Каждый запуск создаёт собственный временный Docker PostgreSQL на случайном порту
loopback. Данные находятся в tmpfs, без host volumes. Применяются существующая
schema, loader и production SQL reader. Все 100 исходных документов сверяются с
snapshot. Runtime получает отдельную роль с SELECT только core/raw; audit и
производственная БД недоступны. Контейнер удаляется при выходе, в том числе при
исключении. После SIGKILL временный контейнер может
остаться; удалять только конкретный контейнер прерванного запуска после
проверки имени и label, заданных в `defense_data.py`.

DB impact: создаётся и заполняется только временная БД. Рабочая schema, SQL,
repository и данные не меняются; новая миграция не требуется. Reader исполняет
настоящие запросы поиска/ранжирования/связей/точных снимков, а не копию их логики.

По умолчанию `web=disabled`: это воспроизводимая проверка внутренних данных и
честного ответа при недоступном web. `--web live` — отдельный эксперимент; его
результаты нельзя смешивать с fixed-data benchmark. Обычный продуктовый режим
не меняется. Runtime/модели настоящие, HTTP admission, транспорт MCP, UI и PDF
этот runner не проверяет. Для стенда отдельно нужны существующие HTTP smoke.

## Команды

Из `backend/`, с Docker и настроенными live-ключами в `.env`:

```sh
PYTHONPATH=. .venv/bin/python -m evals.defense_bank --check
PYTHONPATH=. .venv/bin/python -m pytest -q tests/test_defense_evals.py tests/test_eval_harness.py
TEST_DEFENSE_POSTGRES=1 PYTHONPATH=. .venv/bin/python -m pytest -q tests/test_defense_evals.py -k disposable
PYTHONPATH=. .venv/bin/python -m evals.defense_run --suite pilot --output evals/results/defense-pilot
PYTHONPATH=. .venv/bin/python -m evals.defense_judge --run evals/results/defense-pilot
PYTHONPATH=. .venv/bin/python -m evals.defense_run --suite full --output evals/results/defense-full
PYTHONPATH=. .venv/bin/python -m evals.defense_judge --run evals/results/defense-full
```

Это оплачиваемые вызовы текущего Master и доменных моделей. Семантический review
использует только ту же настроенную модель проекта (сейчас GLM), без автоматической
подмены другой моделью. `same_model_as_subject=true` явно фиксирует зависимость
оценки: это не независимый судья и не человеческая приёмка. `.env` не редактируется.

Пилот содержит 20 сценариев всех девяти категорий. `--case M07` выбирает сценарий
внутри suite; `--repetitions 3` повторяет целый диалог с новой сессией. Для точного
повтора holdout-сценария укажите `--suite full --case …`. Каждой попытке нужен
новый output-каталог. Resume середины диалога не подделывает LangGraph state:
прерванный сценарий повторяется целиком в новом запуске. `--concurrency 1..4`
ограничивает независимые диалоги, внутри реплики последовательны.

Повтор судьи сохраняется отдельно: `--label second`. Старый вывод не затирается.
`defense_report --run <dir> --judge-label configured` пересобирает отчёт без LLM.
`--regrade` пересчитывает точные проверки на архивных ответах, сохраняет отдельный
`regraded-checks.json` и hash оценщика; исходные trace и результаты не изменяются.

## Оценка

Главная метрика: полностью выполненные сценарии / все запланированные попытки.
Для диалога должны пройти все обязательные шаги. Для составного вопроса отдельно
считается выполнение каждого требования. Существенная фактическая ошибка даёт
FAIL независимо от количества закрытых остальных частей. PARTIAL — полезная, но
неполная работа. INCOMPLETE, NOT_REVIEWED, UNCERTAIN не становятся PASS.

Точные проверки сверяют структуры, source paths, допустимые инструменты, бюджеты,
идентичность, состав финалистов и полноту отбора. Отсутствие применимых проверок
значений обозначается NA, не является доказательством фактической точности.
Судья получает критерии, ответ, UI blocks, реально наблюдавшийся контекст и
исходные документы. Проверяются полнота его оценок, буквальность цитат и разрешимость
JSON-путей. Пропуск части ответа может иметь пустую цитату; critical error требует
непустой цитаты и ссылки. Смысл доказательства остаётся предметом отдельного review.
Никакой семантической проверки русской прозы regex-правилами нет.

Latency отдельно от смыслового успеха; p50/p95 включают ошибки и не являются SLO
успешных ответов. Токены и число вызовов включают setup и все наблюдаемые доменные
повторы. Цена в долларах неизвестна без provider billing; она не выдумывается из
устаревшего прайса. Судейские токены считаются один раз на реальный вызов.

`manifest.json` фиксирует версии, модели, настройки, hashes кода/банка/снимка и
грязное состояние checkout. `*.json.gz` сохраняются атомарно после каждой реплики;
там есть все source reads, ToolResults, before/after state, usage и latency.
Скрытые рассуждения и ключи не сохраняются. `source.json.gz` — полный исходный
набор прогона. Вход судьи и необработанный итоговый JSON сохраняются отдельно.

Автоматические verdicts предварительные. Перед защитой нужно проверить спорные
случаи и выборку PASS человеком, сверить согласие судьи с этой разметкой. Отдельный
review Codex тоже является AI-review, его нельзя называть человеческой приёмкой.
Старые ошибки не удаляются, удачный повтор не заменяет неудачную попытку.
