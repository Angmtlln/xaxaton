# ALEPH — максимум аналитической ценности из существующего JSON

Версия 0.2 · 2026-09-05. **Задание для разработчика, не runtime-prompt.**

## Основание и границы уверенности

Основание — приложенный аудит Codex, сохранённый как `CODEX_DATA_AUDIT.md`. Он проверял реальные локальные данные офлайн: finance/legal/comparison через registry; full check — через `_compact_check` и тестовую оболочку CheckResponse. Он НЕ подтверждает текущую production-конфигурацию, живой ответ LLM или каждый возможный путь сырого JSON.

Автор этого документа прочитал аудит, но не выполнял код репозитория и не получил сам `contractors_audit.snapshot.json`. Все перечисленные существующие пути взяты из аудита и относятся к ToolResult/builders, если не указано иначе. Пути сырого JSON и смысл непонятных названий подтвердить в репозитории. Не придумывать отсутствующие поля.

**Решение:** исправлять потери данных, а не подгонять методологию под искусственно урезанный ToolResult. Не отправлять весь сырой JSON модели.

## 1. Четыре уровня аналитической ценности

1. **Наблюдения источника:** показатели, история, события, статусы, описания, положительные и отрицательные признаки. Не ограничиваться текущим `facts`-каталогом: это результат преобразования, не полный источник.
2. **Детерминированные расчёты:** отношения, изменения, состав, сопоставимость периодов и полнота. Формула, входы и ограничения проверяются кодом.
3. **Связанные интерпретации:** Master сопоставляет финансы, судебные сведения, статус, деятельность и задачу пользователя. Его вывод не обязан существовать среди заранее прописанных findings.
4. **Гипотезы и следующие вопросы:** Master указывает возможное объяснение и необходимые подтверждения. Гипотеза не повышается до наблюдения источника и не сохраняется в factual memory как факт.

Реализация первых двух уровней — без дополнительного LLM. Третий/четвёртый — существующий Master synthesis.

## 2. Исправляем существующий путь, не строим новую платформу

```text
исходный сохранённый JSON / repository
  → существующие builders + общая нормализация доступных разделов
  → полный локально доступный набор данных / ссылка на снимок
  → тематическая проекция для текущего вопроса
  → Master + короткий Risk Playbook
  → ответ и backend-гидратированные артефакты
```

Понятия «полный набор» и «проекция» обозначают границы, а не требование новых классов, сервисов, БД или двух копий снимка. Расширить текущие функции и контракты. Общие преобразования должны переиспользоваться FC/F/L/C, чтобы они не расходились по единицам и семантике.

Не возвращать online verifier/repair или legacy Summary в live path ради этого задания. Не менять провайдер/модель, лимиты, frontend-фреймворк. Не разбирать фиксированный JSON моделью вместо обычного кода.

## 3. Сначала инвентаризация source → Master, затем сразу исправления

Коротким офлайн-проходом по доступной выгрузке собрать реальные поля и варианты структур, включая вложенные массивы и содержательные текстовые поля. Проверять не только ООО «ГДК»; количество и выборку компаний зафиксировать. Если вся выгрузка мала, пройти целиком. Разведку не превращать в новую многодневную задачу.

Для каждого бизнес-поля документировать:

`raw JSON path → смысл/тип/единица/период → builder → ToolResult → normalized_tool_context → способ доступа Master`.

Зафиксировать одну из причин состояния: передано; доступно локально по запросу; теряется при преобразовании; отсутствует в источнике; намеренно исключено с причиной. Неизвестная семантика — отдельная пометка, не угаданное значение.

Технические служебные поля, секреты и нерелевантные персональные данные не отправлять модели ради процента покрытия. Наличие поля у одной компании не означает заполненность у всех. Результат — компактный `docs/DATA_COVERAGE.md`, а не runtime-словарь на тысячи токенов.

## 4. Конкретные потери по аудиту — приоритет P0/P1

| Узел | Что аудит установил | Что сделать |
|---|---|---|
| Финансы | FC `fin.series` содержит `total_assets`, `current_assets`, `bankroll`, `short_term_total`, `long_term_total`, а также дебиторку; F оставляет выручку, прибыль, капитал и кредиторку | Раскрыть F доступные статьи баланса и историю. Точный ключ дебиторки и семантику `bankroll` проверить. Не запускать full check ради балансовой статьи |
| Legal | FC содержит `court.by_year`; L теряет ряд, часть стадий попадает только в evidence display из-за лимита восьми metrics | Передать роли, годовые агрегаты и доступные стадии структурированно. Не читать числа из `evidence.display_value` как из основного хранилища |
| ИП | FC содержит `active_count`, `active_amount`, до пяти `recent_active` с номером/датой/суммой; C содержит иной набор (`total_count`, `active_amount`) | Уравнять определения, явно различать active/total. Сохранить все доступные записи локально; для выбранных передавать полноту выборки |
| Статус | Builder создаёт `company.status_reason`, но FC/L/C его не доставляют Master | Протянуть причину без нового вывода о статусе; сохранить исходную формулировку |
| Оценки | В L company-поля risk/ZСК есть, но нормализация их теряет; в других путях неполная передача | Компактный общий identity/status-context доступен во всех применимых путях; два поля не смешиваются |
| Актуальность | `freshness.report_date`/`company.report_date` есть в ToolResult, но отсутствуют у Master | Сохранить доступную дату и provenance; при несовпадении не выбирать молча одну дату |
| Положительные данные | FC оставляет `positive.count`, число контрактов; сайт и содержательные признаки не передаются | Найти их в raw/builders. Если есть — передавать содержание/тип и источник, не только count. Успех исполнения не достраивать |
| ОКВЭД | `okved.is_many` — внутренний признак количества ≥10, не маркер видов деятельности из ответа кейсодателя | Развести смыслы; раскрыть реальные коды/основной вид/описания, если есть. Не создавать «массовый ОКВЭД» из количества |
| Comparison | Отбрасывает финансовые ряды, истца, стадии и детали; выбирает последние годы независимо | Сравнение читает те же нормализованные разделы; компактный ответ не равен обеднённому trusted context. Сопоставлять годы по правилам раздела 7 |
| Полнота | Некоторые FC-агрегаты заполняют пропуски нулём; test-shell `SUCCEEDED` при пустой прибыли не отражает качество | Исправить на уровне агентных данных. Отделить execution success от completeness. Не считать тестовую оболочку доказательством live-багов |

P0: ложные нули, компания/период/единицы, потеря дат и статусов, чужой домен вместо нужного, политика «метка = запрет».

P1: расширение finance/legal/comparison и содержательных профильных сведений. Не откладывать очевидные пробросы полей ради проектирования универсального extractor.

Для других разделов (связи, проверки, лицензии, ресурсы, закупки и т.д.) аудит не доказывает наличие полезных деталей в raw. Просмотреть источник и использовать обнаруженное; не создавать фиктивные сведения или новые внешние источники.

## 5. Полнота и происхождение — без новой тяжёлой модели

Использовать существующие metadata/evidence, расширив минимально. Для наблюдения должно быть понятно: компания, смысл, значение, единица, период или дата, исходный путь и снимок/дата источника (если известна).

Различать:
- observed value, включая явно подтверждённый ноль;
- explicit null / отсутствие поля / недоступность источника;
- invalid value / несовместимые единицы;
- not included in current projection;
- derived value с формулой и входами.

`status=success` — исполнение инструмента; это не `coverage=complete`. Не восстанавливать причины отсутствия доступа, если в JSON их нет.

Сумма неизвестных компонентов не становится нулём. При частичных известных компонентах можно вернуть частичную сумму с явным scope; не называть её полной. Не выводить число уникальных дел из суммы стадий, если стадии могут пересекаться. Не придумывать precision или «confidence 0.9».

Идентификаторы evidence включают компанию/снимок/период или иную достаточную область уникальности. Производный показатель ссылается на все входы и версию формулы, не маскируется под строку внешнего отчёта.

## 6. Что вычислять кодом из уже имеющихся значений

Это предлагаемый набор расчётов, не утверждение об их нынешней реализации. Добавлять только после подтверждения семантики полей. Нет данных для формулы — `not_calculable` с причиной, а не LLM-оценка.

| Расчёт | Формула / условия | Что он НЕ устанавливает |
|---|---|---|
| Абсолютное изменение | `x(t2) − x(t1)`; один показатель, единицы и согласованный периметр | Причину изменения |
| Темп изменения | `(x(t2)/x(t1) − 1) × 100%`; для осмысленной положительной базы; `YoY` только при сопоставимых соседних годах | Рост с нуля; процентную «нормальность» перехода от убытка к прибыли |
| Доля капитала в активах | `capitals / total_assets × 100%`, активы > 0, одна отчётная дата | Долю свободных денег; специальный расчёт чистых активов |
| Балансовый оборотный капитал | `current_assets − short_term_total`, когда поля означают оборотные активы и краткосрочные обязательства | Денежный поток, сумму доступных денег или отраслевой норматив |
| Текущая ликвидность | `current_assets / short_term_total`, знаменатель > 0 | Гарантию своевременной оплаты; одинаковую норму для всех отраслей |
| Состав оборотных активов | Деньги/дебиторка/прочие явно раскрытые статьи относительно `current_assets` | Взыскуемость дебиторки, отсутствие ограничений на использование денег |
| Структура обязательств | Краткосрочные и долгосрочные итоги; их доли при полном согласованном составе | Срок каждого платежа. Кредиторку не прибавлять повторно к итогу, в который она уже входит |
| Прибыль к выручке | `profit / proceeds × 100%`, выручка > 0; тип прибыли подтверждён | Чистую маржу, если `profit` — не чистая прибыль; конверсию прибыли в деньги |
| Кредиторка к годовой выручке | Сумма кредиторки на дату / выручка за указанный год | «Процент неоплаченных продаж», сроки оборота, долю банковских кредитов |
| Масштаб требований/ИП | Раздельные суммы к активам, положительному капиталу, годовой выручке; даты/периоды явно показаны | Общий долг, нехватку ликвидности или вероятность проигрыша. При нулевом/отрицательном капитале относительную меру к капиталу не использовать как рейтинг |
| Контекст сделки | Размер и сумма аванса из явно заявленных условий; масштаб относительно подходящих показателей | Проверенный внешний факт сделки или точный невозврат: условия пользователя помечаются отдельно |
| Динамика судебных агрегатов | Раздельные роли/годы и сравнение только при сопоставимой длительности/полноте наблюдения | Тенденцию по одному году или полному прошлому против неполного текущего |

Не добавлять сейчас DSO/DPO без необходимых оборотов и остатков, DSCR без потока и обслуживания долга, EBITDA без составляющих, PD/общий скоринг, отраслевые пороги из головы.

Матрица и коэффициенты — инструменты анализа, не `if ratio → verdict`. Общие формулы не запрещают новые интерпретации Master.

## 7. Сравнение: максимум доступа, а не максимум колонок

Для каждой метрики искать общий сопоставимый период у сравниваемых компаний; сохранять индивидуальные последние сведения отдельно. Отсутствие общего периода явно помечать. Не откатывать важную актуальную негативную информацию ради одинакового старого года.

Не собирать строку «2025» из выручки 2025, прибыли 2024 и капитала 2023. Неполный год и полный год не считать равными. Смешение единиц устранять до расчёта; разные валюты без согласованного курса не сравнивать как одинаковые суммы.

Хранить доступные ряды и legal-детали по каждой компании в scoped trusted context. Менять видимые колонки по вопросу; не требовать три full check для ответа о финансах. Низкая полнота — отдельная неопределённость, не позитивный сигнал.

## 8. Максимум данных без огромного prompt и новой задержки

**Доступность данных агенту ≠ присутствие всех данных в каждом запросе.**

- Все содержательные исходные сведения остаются доступными локально через существующий repository/снимок, а не теряются после `[:8]` или `[:5]`.
- Текущий запрос получает компактное identity/freshness/coverage-ядро и полный релевантный домен в разумном объёме. Метаданные не должны стоить больше полезных значений.
- Годовые ряды можно представлять колонками и строками без многократного повторения длинных labels/evidence. Не удалять истории только ради одинакового размера карточки.
- Для длинных событийных списков: доступное количество, включённое количество, фильтр/порядок отбора, периоды и отметка сокращения. «Всего» означает только действительно известное количество источника.
- Дополнительные детали читать существующими tools через небольшой валидируемый параметр раздела/периода/страницы, если это нужно. Не создавать отдельный tool на каждый показатель, произвольный JSONPath/SQL или filesystem access.
- Сначала использовать уже имеющийся trusted context нужной компании/домена/снимка. Последний legal-результат не является finance cache hit. Обновление одного домена не стирает остальные.
- История текста не дублирует полный ToolResult на каждом turn. Источник данных выбирается без LLM-компрессора.
- Весь playbook подключить один раз в существующие synthesis-инструкции; NOTES/PLAN/AUDIT туда не идут. Проверить включение файла в Docker/build и загрузку по одному каноническому пути; отсутствие плейбука не должно молча игнорироваться. Дисковое кеширование файла не устраняет входные токены модели — замерять реальный payload.

Не менять семантику лимита tool output простым увеличением числа. Уменьшать дублирование и выбирать релевантное; сохранять конечные ограничения. Не выдавать недопоставленные в prompt сведения за отсутствующие у источника.

## 9. Реализация двумя короткими этапами, без повторного проектирования

**A. Data coverage.** Подтвердить маппинг в raw, исправить P0/P1, добавить расчёты и тесты передачи через `normalized_tool_context`. Отдельная логическая фиксация. Не менять UI-дизайн или существующий аналитический runtime.

**B. Playbook.** Подключить v0.2 к существующему Master, убрать противоречащие инструкции и обязательные текстовые «приговоры» из notices. Не менять значения банковских полей и источника. Обновить документацию, проверить небольшой live-набор и зафиксировать отдельно.

Не запускать эти этапы конкурирующими правками одних файлов. В существующей ветке сначала проверить чистоту/дифф; не сбрасывать чужие изменения. Изменения `/report` должны сохранять работоспособность, но не обязаны сохранять ранее ошибочную интерпретацию нулей или стоп-меток.

## 10. Проверки и Definition of Done

Офлайн, без платных LLM:

1. Raw → builder → ToolResult → Master projection: балансовая статья, `status_reason`, даты, bank/ZСК, court years/stages, положительный detail проходят весь путь.
2. Новое содержательное поле, ранее не входившее в `facts`, имеет явный mapping или обоснованное исключение; тест не ограничен старым whitelist.
3. `null`, missing, explicit 0, частичная сумма и усечённый список различаются. FC test-shell success не подавляет gaps.
4. Формулы: единицы, соседние/пропущенные годы, отрицательная/нулевая база, отсутствие одного входа, область компании/снимка, округление и происхождение.
5. Legal-стадии структурированы, не извлечены парсингом evidence display. Арбитраж/ИП не суммируются в общий долг.
6. F/FC дают одинаковое значение одной статьи при одном снимке. C использует ту же семантику, а годы не смешиваются.
7. Пропущенный finance-context не подменяется legal; подробности доступны без повторного полного анализа и без LLM-компрессии.
8. Инструмент с неожиданным разделом/периодом/идентификатором отклоняет аргумент; evidence/UI остаются в пределах своей компании.
9. Короткий playbook присутствует в нужных model calls ровно один раз; NOTES/PLAN/AUDIT не попадают в prompt; online-verifier не возвращён.

Live, небольшое фиксированное число повторов, не бесконечная доводка промпта:

- Полная проверка → «Что с оборотными активами и краткосрочными обязательствами?» → «Почему это важно?».
- «Как менялась судебная нагрузка? Какие периоды действительно сопоставимы?».
- Сравнение 2–3 компаний за сопоставимый период с обозначением пропусков.
- «Мы продаём с отсрочкой» → «Теперь мы покупаем с авансом»: меняется предмет риска, а не исходные факты.
- Один NO_DATA/PARTIAL случай.

Показать исходные данные и ответы, model/domain calls, input/output tokens, wall time, fallback. Сопоставить before/after на одинаковых снимках; указать объём выборки. Дополнительный LLM-этап ради извлечения/плейбука — 0. Базовые вопросы не должны требовать больше model calls только из-за исправленной проекции. Это целевой gate, не обещание неизменной сетевой задержки.

Итоговый отчёт: какие реальные поля восстановлены; что найдено сверх старого `facts`; что вычисляется; что отсутствует в источнике; что только исключено из текущего prompt; какую аналитическую задачу теперь можно решить. Не считать процент всех JSON-ключей единственной метрикой качества.
