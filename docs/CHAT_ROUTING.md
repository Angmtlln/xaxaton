# Выбор действия Master и распознавание ИНН

Два этапа исправления ограничений: свободный выбор действия и корректный ИНН,
затем два адресных чтения, ввод до 4000 символов и восстановление черновика при истечении сессии.
Схема БД, SQL, доменный pipeline и legacy `/api/v1/checks` не меняются.

## Выбор действия

При доступной модели однозначные команды полной проверки сохраняют существующий
прямой dispatch. Для остальных вопросов об одной компании Master получает
`full_company_check`, `get_financial_data`, `get_legal_data` с `tool_choice=auto`.
Он может выбрать чтение либо сразу ответить JSON по trusted context.
Отдельный классификатор или дополнительный LLM-stage не вводится.

Ключевые слова финансов и судов больше не определяют единственный доступный
инструмент в этом online path. Отрицания и перефразирования интерпретирует модель.
Это не гарантия правильного понимания каждого запроса: поведение проверяется
живыми сценариями, отдельно от проверки ограничений исполнения.

До выбора Master получает текущий trusted domain и имеющиеся финансовый/
юридический контексты той же компании. Прежняя проза не заменяет эти сведения.
Точная команда «Объясни проще» сохраняет проход без инструментов. Для произвольного
контекстного вопроса инструменты доступны, но промпт требует использовать уже
полученные сведения, если их достаточно.

После первого адресного чтения доступен только другой адресный раздел: финансы
или юридические данные. Master сам решает, нужно ли второе чтение. Каждый
инструмент разрешён один раз; полная проверка не совмещается с другими чтениями.
Если провайдер предложил оба разных targeted tools одним сообщением, обе схемы
проверяются до чтения, а сами чтения выполняются последовательно под общим lock.
Повтор одного инструмента, сочетание с full check и некорректная пара отклоняются целиком.
После второго инструменты убираются. Лимит свободного выбора — два чтения и три
обычных вызова Master; остальные маршруты сохраняют прежние лимиты. Общий
потолок с отладочным verifier/repair — шесть model calls, recursion limit 16.
Успешные результаты сохраняются отдельно в trusted context. Ошибка одного
чтения не уничтожает другое; ответ имеет partial и явное сообщение о пробеле.
Объединение допускается только для одинаковых ИНН, snapshot_id и report_date. При ошибке свободного выбора backend не угадывает инструмент и не
запускает полную проверку автоматически. Работают прежние ограничения размера,
таймауты, схемы аргументов, проверка идентификатора и backend hydration.

Проверенный входной ИНН можно сохранить активным после уточняющего ответа без
чтения БД. Это не добавляет фактов о компании. Смена ИНН очищает старые trusted
данные и пользовательские условия; неуспешное чтение новой компании сохраняет
прежнее поведение восстановления предыдущей активной компании.

Подборки, ранжирование, сравнение, граф и выбор отдельного отчёта связанной
компании сохраняют отдельные существующие маршруты. Режим без подключённого
Master сохраняет прежнюю детерминированную маршрутизацию.

## Числа во входном сообщении

- Явный `ИНН …` всегда проверяется по формату и контрольным цифрам.
- Идентификатор отдельным сообщением или в простой команде проверки/сравнения
  сохраняет проверки ошибок и неоднозначности.
- В обычном тексте неподписанное число рассматривается как ИНН только при
  правильных контрольных цифрах. Денежная запись и метки суммы/аванса/сделки
  имеют приоритет над таким предположением.
- Явный список ИНН не допускает тихого пропуска неверного следующего номера.
- Сумма `10000000 рублей`, год `2023` и произвольный длинный номер договора
  не вызывают ошибку ИНН. Сравнение использует тот же разбор чисел.

## Веб-поиск

Методология согласована с кодом: новости подключаются только после успешного
`full_company_check`, в том числе выбранного Master. Внешний поиск не включается
для targeted tools и обычных продолжений. Публикации остаются отдельными от
внутренних фактов и анализа.

## Проверки и воспроизведение

Новые проверки поведения находятся в `backend/tests/test_agent_request_routing.py`.
Исходные вопросы `AGENT_EVALS.md` не изменены. Тестовые модели в прежних сценариях
targeted чтения теперь явно выбирают инструмент, вместо ожидания автоматического
вызова по слову в запросе.

Из `backend/`:

```bash
PYTHONPATH=. .venv/bin/python -m pytest -q
docker compose up -d --build api
.venv/bin/python scripts/smoke_agent_routing.py --output /tmp/agent-routing-live.json
```

Живой smoke использует HTTP, настроенную модель и настоящую БД. Проверяет
платёжеспособность, отрицание, сумму сделки, смену темы, «Почему?» и смену компании.
В JSON сохраняются полные ответы и метаданные после каждого хода. Выходной файл
нельзя перезаписать: повторный запуск требует нового пути. Технические проверки
не оценивают смысл каждого утверждения; ответы нужно прочитать отдельно.

## Ввод и истечение сессии

Оба chat endpoints принимают до 4000 Unicode-символов. Форма не обрезает вставку:
при превышении лимита показывает ошибку и оставляет весь текст. Четыре записи
user_context сохраняют до 4000 символов каждая; число записей и TTL не меняются.

При unknown_conversation запрос не выполняется и не отправляется автоматически.
История остаётся на экране, активная компания сбрасывается, запрос возвращается
в поле и переживает перезагрузку страницы. Уведомление объясняет потерю контекста;
следующая отправка создаёт новую сессию, для обращения к компании нужен ИНН.
Кнопка «Новый диалог» после истечения тоже сохраняет черновик.
Новая долговременная память, сводки, PostgreSQL persistence и token budget не вводились.

## Диагностика качества и задержек

В методологии уточнено исправление прежних преувеличений: кассовый разрыв нельзя
устанавливать только по капиталу/выручке/искам, сумму исков нельзя приписывать
конкретным делам без связи, метка ограничения счёта не доказывает блокировку
любого платежа. Это инструкция модели, а не доказательство отсутствия ошибок.
Каждый основной model call пишет run_id, номер, длительность и usage; неуспешный
вызов пишет длительность и тип сбоя. Таймауты не сокращены и дополнительного
LLM-проверяющего нет. Устранение редких задержек до 71 секунды не гарантируется.

.venv/bin/python scripts/smoke_agent_routing.py --suite stage2 --output /tmp/agent-stage2-live.json
