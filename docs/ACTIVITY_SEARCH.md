# Поиск по деятельности и финансовым условиям

`find_companies` фильтрует текущую загруженную базу одновременно по деятельности
и финансовым/правовым условиям. Основные **и дополнительные ОКВЭД учитываются
по умолчанию**, по пожеланию пользователя. Для компании достаточно одного
подходящего кода; несколько совпадений не увеличивают счётчик компаний.

## Использование

- «Найди компании занимающиеся торговлей и с выручкой от 10 млн».
- «Найди компании занимающиеся оптовой торговлей фруктами и с выручкой от 10 млн, покажи первые 5».
- «Найди компании с ОКВЭД 46.7 и с выручкой от 10 млн».
- «Найди компании занимающиеся торговлей только основной ОКВЭД» — явное ограничение основным видом.

Эти целиком распознанные команды вызывают SQL напрямую; модель формирует
объяснение по результату. Сложные формулировки остаются в существующем native
маршруте. Явно названная через «занимающиеся …» / «по деятельности …» деятельность
закрепляется backend и не исчезает, даже если модель передаст только выручку.
Применённые условия показываются над таблицей. Совпавшие коды и описания
сохраняются в проверенных данных backend, но не выводятся в строках таблицы.

## Источник и ограничения

Источник JSON: `report.kindsOfActivityInfo.mainKindOfActivity.{code,description}`
и `otherKindsOfActivity[].{code,description}`. Загрузчик уже сохраняет их в
`core.activity_codes`: 100 основных записей, 2128 дополнительных у 97 компаний
в локальном наборе, проверенном 6 сентября 2026.

Отдельная полная копия классификатора не добавлена. Словарь здесь — реальные
названия ОКВЭД из загруженных снимков. Поиск использует PostgreSQL full-text
с конфигурацией `russian`: «торговля» и «торговлей» совпадают. Все значимые слова
должны совпасть в описании одного кода, а не в разных дополнительных видах.
Это лексический поиск со словоформами, не универсальный поиск синонимов:
произвольные разговорные названия отраслей могут не найтись. Код пользователя
ищется вместе с дочерними кодами: 46.7 включает 46.73 и 46.73.1.

ОКВЭД показывает заявленную деятельность, не доказывает фактические продажи.
Порог выручки относится ко всей компании за её последний доступный финансовый
год, а не к выручке конкретного направления. Отсутствующие ОКВЭД/описания не
считаются совпадением. Пустая подборка не приводит к поиску без фильтра.
Альтернативы/исключения вроде «не торговля» пока не поддерживаются.

## DB impact и запуск

Новая идемпотентная миграция `005_shortlist_activity.sql` добавляет `snapshot_id`
в существующую read-only view. Таблицы и исходные карточки не изменяются.
Для новой базы это же определение включено в `schema.sql`.

```bash
docker exec -i contractors-db psql -U postgres -d contractors -v ON_ERROR_STOP=1 \
  < backend/db/migrations/005_shortlist_activity.sql
docker compose -f backend/docker-compose.yml up -d --build api
```

Миграция применена к локальной Docker БД. Фильтрация через EXISTS выполняется
до count/order/limit, поэтому финансовые условия и деятельность соединяются
через AND без дублей. Значения параметризованы; SQL-операторы из запроса не исполняются.

## Выбор N компаний по показателям

Поддерживаются выручка, прибыль, сумма исков к компании и число исполнительных
производств. Это последовательная сортировка проверенных чисел, без общего
рейтинга надёжности и весов.

- «Найди торговые компании с выручкой от 10 млн и выбери 5 с наибольшей прибылью».
- После поиска: «Из найденных выбери 3 с минимальной суммой исков».
- «Выбери 5 по прибыли и количеству исполнительных производств» — сначала
  предложение порядка, затем «Да». Можно изменить показатели или написать
  «Выбери 3» до подтверждения. «Нет» отменяет предложение.
- «Выбери 5 сначала по прибыли, затем по сумме исков» задаёт приоритет явно
  и выполняется сразу. Следующий показатель используется только при равенстве
  предыдущего; при полном равенстве порядок задаёт ИНН.
- «Почему эти?» использует сохранённый результат без нового поиска.

По умолчанию выбираются 5, допустимо 1–25. Выручка и прибыль — по убыванию,
иски и производства — по возрастанию; явное направление имеет приоритет.
Без предыдущей подборки можно выбрать по показателю из всей базы. Если подборка
есть и новый запрос не содержит новых фильтров, используются её условия.
«Из найденных» без сохранённых условий вызывает уточнение.

Backend хранит нормализованные фильтры отдельно от видимых строк и текста
assistant. Новый выбор повторяет фильтры по текущей базе и не ограничивается
ранее показанными пятью строками. Новый поиск сбрасывает ожидающее подтверждения
предложение. Контекст живёт в текущей in-memory сессии и теряется при её истечении
или перезапуске API.

Расширение `FindCompaniesArgs`: `ranking` — упорядоченный список из 1–4 уникальных
`{metric: proceeds|profit|claims|enforcement, order: asc|desc}`. При его наличии
прежние `sort_by/order` не используются для сортировки. Многокритериальный порядок
не может поступить в SQL напрямую от native model tool call: его подтверждает
backend по пользовательскому запросу/сохранённому предложению.

`ShortlistData` сохраняет `filters`, `ranking`, `eligible_total`, `notes` и дату
снимка в строках. `total` — число совпадений фильтра до исключения неполных данных;
`eligible_total` — число компаний с заполненными выбранными показателями.
NULL исключается из ранжирования, проверенный ноль остаётся значением. Если
кандидатов меньше N, показаны все доступные; ограничения не ослабляются.

Таблица показывает порядок, количество пропусков, финансовый год и дату снимка.
Для денежных показателей, по которым идёт выбор, выводится сумма до копеек вместо
округления до миллионов. Финансы относятся к последнему доступному году каждой
компании; разные годы сопровождаются оговоркой. Сумма исков и количество
производств используют прежние определения витрины, не только действующие дела.

Разбор команд ограниченный: незнакомые дополнительные условия не отбрасываются,
а вызывают просьбу сначала задать отдельный поиск. «Лучшие вообще» требует
показателя. Рентабельность, рост, веса и выбор под условия сделки в v1 не входят.

### Миграция и запуск

`006_shortlist_ranking.sql` идемпотентно добавляет `report_date` в существующую
read-only view. Таблицы и исходные данные не меняются; то же определение находится
в `schema.sql`. Сначала применяется миграция, затем обновляется API:

```bash
docker exec -i contractors-db psql -U postgres -d contractors -v ON_ERROR_STOP=1 < backend/db/migrations/006_shortlist_ranking.sql
docker compose -f backend/docker-compose.yml up -d --build api
```

Проверки и измерения: [приёмка выбора по показателям](RANKING_ACCEPTANCE.md).

### Две фразы в одном запросе

Поддерживается: «Найди торговые компании с выручкой от 100 млн рублей.
Покажи 5 с наибольшей прибылью». Условия поиска отделяются от команды
сортировки точкой, точкой с запятой, запятой, переносом строки или «и».
Порог, направление и количество сохраняются; неизвестные условия не отбрасываются.
DB impact: отсутствует, меняется только разбор команды. Регрессия — `tests/test_ranking.py`.
