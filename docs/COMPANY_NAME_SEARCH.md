# Поиск компании по названию

## Пользовательский сценарий

В чате можно написать «Проверь Электролид» или «Какая выручка у Электролид?».
Поиск работает только по загруженным карточкам. Единственное точное совпадение
продолжает исходный запрос; несколько точных либо только частичные совпадения
показывают до пяти вариантов с ИНН и адресом. Выбор кнопкой, ИНН или словом
«вторая» продолжает исходный вопрос. Приветствие/новый запрос отменяет прежний
выбор; «Объясни проще» у списка поясняет выбор без чтения старой активной компании.

Подсказки в поле ввода появляются после двух символов и паузы 250 мс.
Без `@` ищется весь текст, внутри вопроса — фрагмент от последнего `@` до курсора:
«Какая выручка у @Электролид». Выбор вставляет название и ИНН в черновик.
Стрелки выбирают вариант, Enter подтверждает выделенный вариант, Escape закрывает
список. Выбор подсказки сам сообщение не отправляет. Обычная отправка без выбора
тоже поддерживает названия — их извлекает модель после отправки.

Регистр, `е/ё`, кавычки и лишние пробелы не влияют на поиск. Обозначения ООО,
АО, ПАО, ОАО, ЗАО, ИП и их полные формы удаляются только в начале поискового
ключа. Сначала точное совпадение, затем начало и часть названия; внутри группы
сортировка по ИНН. `%`, `_` и обратный слеш — обычные символы. Опечатки,
брендовые синонимы, внешние реестры и сравнение по нескольким названиям не входят
в эту версию. При отказе модели можно выбрать подсказку или отправить ИНН.

## Контракты и состояние

`GET /api/v1/companies/search?q=Электролид&limit=5` возвращает `rows`, `total`,
`exact_total`. Аргумент `q`: 2–256 символов, `limit`: 1–5. Каждый вариант содержит
`inn`, `name`, `full_name`, `address`, `snapshot_id`, `match` (`exact/prefix/partial`).
Количество совпадений считается до LIMIT. Нулевой результат означает отсутствие
в нашей базе, а ошибка источника остаётся отдельной ошибкой.

Путь чтения: repository → CompanyDataReader → direct/MCP → PostgreSQL.
Типы находятся в `backend/app/domain/company_search.py`; MCP публикует восьмую
операцию `search_companies`, схема существующих операций не меняется.

Перед обычной маршрутизацией по ИНН `name_resolution.py` использует существующий
LangChain `create_agent`: максимум один вызов модели и один `search_companies`
с `return_direct`. Поисковый аргумент обязан быть дословным фрагментом текущего
сообщения. Модель не назначает ИНН: его выбирает backend по проверенной выдаче.
Обычные явные ИНН, точные команды объяснения и существующий подбор по критериям
не требуют этой стадии. Общий deadline сохраняется; верхняя граница model calls
увеличена на один (до семи с debug verifier), tool calls учитывают поиск отдельно
от прежнего бюджета аналитических инструментов (в ответе до трёх суммарно).

`pending_company_search` отдельно хранит исходный вопрос, строку поиска,
идентификатор выдачи и до пяти кандидатов. Активная компания до выбора не меняется.
После выбора исходный вопрос передаётся прежней маршрутизации с проверенным ИНН.
Смена компании использует прежнее очищение аналитического контекста.

При активной компании точные продолжения «а что у них с финансами?»,
«а что у них с судами?», «покажи финансы» и «покажи суды» пропускают распознавание
названия и при подключённой модели. Master получает текущий контекст и сам
выбирает ответ или адресное чтение. Дописанное название новой компании сохраняет
обычный поиск. Это исправление маршрутизации не меняет БД.

Ответ чата может содержать backend-owned блок `company_choice`. Кнопка отправляет
дополнительное необязательное поле `company_selection: {search_id, inn}` на обоих
chat endpoints. Формат обычного сообщения не меняется. Сервер отклоняет чужую,
истёкшую или уже использованную выдачу; старые кнопки также отключены в интерфейсе.

## DB impact и запуск

Миграция `backend/db/migrations/008_company_name_search.sql` добавляет SQL-функцию
нормализации и read-only view последних карточек, выдаёт SELECT/EXECUTE роли MCP.
Схема синхронизирована, setup MCP применяет миграцию после настройки роли.
Исходные записи и аудит не переписываются; расширения PostgreSQL не нужны.
Для текущего небольшого датасета используется ограниченная проекция; отдельный
поисковый индекс не вводится. Перед масштабированием нужен замер на новом объёме.

Из `backend/` при работающей базе:

```bash
docker compose exec -T db psql -U postgres -d contractors -v ON_ERROR_STOP=1 < db/migrations/008_company_name_search.sql
docker compose build api
docker compose up -d --no-deps --force-recreate company-data-mcp api
```

`--no-deps` сохраняет текущий контейнер БД и его привязку портов. Миграция
идемпотентна. `/api/v1/companies`, `/api/v1/checks` и `/report` совместимы.

Реальные SQL, direct/MCP parity, повторное применение миграции, права чтения,
одноимённые компании и буквальные спецсимволы проверяются в отдельной временной
БД тестом `test_name_search_sql_and_mcp_parity` из `tests/test_mcp_database.py`.
Команда подготовки и запуска — в [MCP_DATA_ACCESS.md](MCP_DATA_ACCESS.md).

Ручная desktop-приёмка: название → подсказка; `@` внутри вопроса → выбор;
неоднозначный поиск → кнопка/«вторая»; новый запрос → старый выбор недоступен;
точное название → финансовый вопрос → «Объясни проще». Мобильные доработки отложены.
