# MCP: планируемый доступ к данным контрагентов

Статус на 06.09.2026: обсуждена архитектура и предварительная оценка.
MCP-сервер, клиент, настройки и интеграционные тесты ещё не реализованы.
Этот документ описывает будущую работу, а не действующий API.

## Задача и смысл MCP

По сообщению пользователя MCP входит в требования заказчика. Точная исходная
формулировка пока не подтверждена: прежний PROJECT_CONTEXT описывал MCP как
необязательную эмуляцию доступа к системе проверки контрагентов.
Рабочая трактовка — предоставить нашему приложению стандартный интерфейс
чтения карточек и поиска через отдельный MCP-сервер.

MCP связывает приложение-клиент с сервером инструментов и данных.
Сервер обращается к PostgreSQL обычным драйвером и SQL. Наш backend может
сам быть MCP-клиентом; внешний harness для этого не требуется. MCP не
заменяет базу, не рассчитывает риск и не требует дополнительной LLM.

Основание: [архитектура MCP](https://modelcontextprotocol.io/docs/learn/architecture)
и [официальный Python SDK](https://github.com/modelcontextprotocol/python-sdk),
проверенные при оценке через официальную документацию и Context7.
При реализации нужно закрепить совместимую версию SDK для сервера и клиента.

## Текущий и целевой путь данных

Сейчас загрузчик `backend/scripts/load_snapshot.py` импортирует входную выгрузку
в PostgreSQL. Исходный объект сохраняется в `raw.report_documents.document`
(JSONB), нормализованные сведения — в `core.*`.
`backend/app/infrastructure/repository.py` читает снимки и отдельно записывает
результаты проверок в `audit.*`. Полная проверка и targeted capabilities
получают снимки через этот repository. Офлайн-демо и тестовые фикстуры могут
читать файл напрямую: это отдельные режимы, не рабочий DB path.

```text
Сейчас: backend → repository → PostgreSQL

План:   backend → MCP-клиент → MCP-сервер → PostgreSQL
                                            ↑
                             исходные JSON загружены заранее
```

Для демонстрации можно использовать существующую настоящую БД с данными
выгрузки. Эмулируется внешний источник заказчика, а обмен MCP должен быть
реальным. Новый импорт или перенос JSON не требуется.

## Предлагаемый объём реализации

- Небольшой Python MCP-сервер с Streamable HTTP во внутренней сети Docker и
  клиентский адаптер чтения в backend. Публичный интернет-доступ не нужен для демо.
- Узкие операции: карточка по ИНН, существующий поиск/каталог с фильтрами,
  ограниченные пакеты точных снимков для подбора и данные для проверки связей.
  Имена новых MCP tools пока не являются зафиксированным API.
- Повторно использовать текущие SQL и семантику фильтров. Покрыть чтения полной
  проверки, finance/legal, сравнения, поиска, подбора, связей и company endpoints.
- Сохранить документ, ИНН, идентификаторы снимка/компании, дату и метаданные,
  необходимые текущим builders и аудиту. Проверять структуру и точность
  сериализации дат и чисел на границе MCP.
- Только разрешённые чтения с ограничениями размера и времени; без инструмента
  произвольного SQL. Для сервера предусмотреть роль БД только на чтение.
- Различать отсутствие компании, неполные данные, ошибку формата и недоступность
  MCP. Сохранить существующие правила частичной кросс-проверки: её сбой не
  отменяет основной анализ. Не выдавать транспортную ошибку за отсутствие данных.
- Предусмотреть явно выбираемый режим direct/MCP для проверки и перехода.
  В MCP-режиме не делать скрытый fallback к прямому чтению БД.
- Факты, provenance, Master Agent и рендеринг остаются в существующих слоях.
  Запись аудита и чтение сохранённых прогонов остаются отдельным DB-механизмом.
  `/api/v1/checks`, `/report` и привычные действия пользователя сохраняются.

DB impact: изменения схемы хранения не ожидаются. Если добавляются DB-роли
и grants, оформить их миграцией и проверить запрет записи; данные не переносить.
В этой документационной задаче SQL и БД не меняются.

## Этапы, стоимость и приёмка

1. Один сквозной проход по ИНН через MCP с проверкой совпадения исходных данных.
2. Переключение остальных чтений, пакетных запросов и поиска.
3. Проверка ошибок, регрессии, запуска Docker и инструкции демонстрации.

Предварительная оценка для одного разработчика: 0,5–1 рабочий день на узкий
проход; 1–3 рабочих дня суммарно на все текущие чтения с тестами. Это оценка,
не замер или гарантия срока. Интеграция реальной системы заказчика оценивается
после получения её контракта, условий сети и авторизации.

MCP не добавляет модельных вызовов, поэтому рост расхода LLM-токенов из-за
самого протокола не ожидается. Он добавляет процесс/контейнер и сетевой обмен;
задержку и размер ответов нужно измерить, числового SLA пока нет.

Приёмка будущей реализации:

- Вызвать MCP отдельным клиентом и прочитать карточку из БД.
- Сверить исходный документ, идентификаторы и рассчитанные факты в direct/MCP.
- Проверить полную проверку, targeted вопросы, сравнение, поиск, подбор и связи;
  убедиться, что эти чтения действительно прошли через MCP.
- Проверить неизвестный ИНН, неполную карточку, ограничения пакета, повреждённый
  ответ, таймаут и отключение сервера без скрытого обхода MCP.
- Проверить запрет записи серверной ролью, сохранение аудита и legacy API.
- Зафиксировать задержку и ошибки MCP без журналирования секретов и полных JSON.
- Выполнить живой сценарий через чат. Структурные тесты и совпадение фактов
  оценивать отдельно от качества аналитической прозы.

Для пользователя сценарий остаётся прежним: открыть чат, ввести ИНН и задать
вопрос. Для демонстратора добавятся запуск MCP и наблюдаемые обращения к нему.
