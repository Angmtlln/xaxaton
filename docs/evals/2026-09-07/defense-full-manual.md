# Защитный eval: ручная смысловая оценка

Дата: 7 сентября 2026.  
Агент под проверкой: `z-ai/glm-5.3-flash`.  
Набор: 150 независимых сценариев (194 оцениваемые реплики, включая многотуровые диалоги).  
Данные: изолированная PostgreSQL с неизменными 100 карточками; веб-поиск отключён.

## Методика

Это ручная оценка Codex по сохранённым запросам, ответам, вызовам инструментов и проверенным данным из карточек. Внешняя модель-судья и её API не использовались. Сценарий считается пройденным, только если агент выполнил существенную часть вопроса и не подменил факт догадкой, не отказался от доступной функции и не испортил контекст диалога.

Технические нарушения учитываются отдельным списком: лишний инструмент сам по себе не превращает содержательно правильный ответ в смысловой провал.

- Полный прогон: `F16`, `F20`; `N07`; `R02`, `R04`, `R07`, `R08`, `R11`, `R12`, `R14`, `R15`; `S06`, `S08`, `S12`; `C04`, `C05`, `C08`, `C09`, `C10`, `C12`, `C16`, `C21`, `C23`, `C24`; `M13`, `M14`, `M17`.

После повторной сверки с требованиями банка `F12`, `L06`, `L09`, `N08` и
`E09` переведены из FAIL в PASS. Подробное основание переразметки и разбор
каждого оставшегося FAIL находятся в `defense-failures-review.md`.

## Что исправлять первым

1. Починить маршрутизацию shortlist и сравнения: простые запросы `R02`, `R04`, `R07`, `R08`, `R12`, `R14`, `C09`, `C16`, `C23`, `C24`, `S08`, `S12` не должны требовать лишнего уточнения или завершаться fallback.
2. Устранить потерю trusted context, из-за которой доступные данные объявляются `NO_DATA` (`F16`, `F20`, `C12`), а обычный справочный вопрос ошибочно пытается резолвить компанию (`N07`).
3. Не превращать баланс в доказательство механизма: «рост финансируется отсрочками», «компания отгрузила работы», причина блокировки или ИП допустимы только как явно помеченные гипотезы с объяснением границы данных.
4. Убрать runtime fallback в составных запросах (`C05`, `C08`, `C10`, `C21`) и потерю trusted context в многотуровых (`M13`, `M14`, `M17`).
