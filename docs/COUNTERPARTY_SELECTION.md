# Агентный подбор под задачу сотрудничества

В чате можно попросить: «Подбери 3 лучших поставщиков: компании занимающиеся
торговлей и с выручкой от 100 млн. Работа без аванса, важна устойчивость поставок».
Если цель не указана, агент спрашивает, выбираем ли поставщика, покупателя или
партнёра. Обычный поиск и явная сортировка по прибыли/выручке работают по-прежнему.

## Что происходит

1. `select_counterparties` применяет существующие SQL-фильтры, без ranking и
   исключения компаний только из-за незаполненных показателей сортировки.
2. До 50 совпадений разбираются целиком, независимо от прежних видимых строк.
   При 51 и более агент просит сузить фильтры до анализа карточек. При нуле
   совпадений условия не ослабляются.
3. Финансовые и правовые строители готовят профили из точных `snapshot_id`,
   выбранных SQL. Первый проход содержит ограниченные факты и три последних
   доступных финансовых периода. Полные отчёты и внешние новости не запускаются.
4. LLM составляет мини-сводку каждой компании: пакеты до 10, не более двух
   одновременно. Затем один вызов сопоставляет все сводки и проверенные значения,
   выбирает до пяти финалистов и объясняет выбор/отсев каждого кандидата.
5. Финалисты сравниваются существующим строителем финансовых и правовых данных
   на тех же снимках. Master формирует рекомендацию и может переставить финалистов.
   При одном кандидате таблица не создаётся.

В ответе показаны условия и количество рассмотренных компаний, рекомендация,
мини-сводки финалистов и таблица. Статусы этапов передаются существующим потоком.
Причины отсева доступны через «Почему не выбрали компанию X?». «Почему эти?» и
«Объясни проще» не запускают новых domain tools. При смене цели используются
сохранённые профили; при смене фильтров выполняется новый поиск. Контекст живёт
в текущей in-memory сессии; перезапуск API его сбрасывает.

## Контракты и ограничения

`SelectCounterpartiesArgs`: `filters` (существующие условия `FindCompaniesArgs`,
без ranking), `goal`, `preferences`, `finalists` (1–5, по умолчанию 5).
Сортировка/лимит отображения внутри filters не ограничивают аналитический охват.
Результат хранит фактические profiles отдельно от LLM reviews/decisions,
финалистов и результата comparison. ИНН и evidence проверяются в рамках каждой
компании; каждый пакет и решение должны охватывать всех переданных кандидатов.

Никакого общего балла, весов или пересчёта банковских оценок нет. Пропуски не
равны нулям. Неполнота источников отличается от незавершённого прохода: завершённый
отбор может иметь ограниченную доказательную базу. При сбое пакета глобальные
победители не выбираются; готовые мини-сводки сохраняются, ответ обозначает
незавершённость. Чужие ИНН/URL в итоговом ответе приводят к fallback без ремонта
прозы. Свободные выводы проверяются поведенчески, не семантическими regex.

На один ход — один внешний tool call; отдельный бюджет подбора включает до
8 model calls (маршрутизация, пакеты, выбор, итог и возможное исправление формата).
При превышении длины текстового поля мини-сводки разрешена одна попытка сокращения
на весь ход, внутри того же бюджета/deadline. Исправлять можно только слишком
длинные поля; остальные поля, включая ИНН и evidence_ids, должны сохраниться.
Другие ошибки схемы, неверные ссылки и ошибки провайдера не повторяются.
`metadata.repair_attempts` показывает использование этой попытки; она не является
семантической проверкой прозы. Если бюджет исчерпан, сохраняется partial.
Общий deadline
не более 300 секунд и учитывает более короткий runtime deadline. Каждый вызов
ограничен существующим model timeout. Внутренние вызовы используют закреплённую
в диалоге модель Master через `create_agent`. Usage и длительность этапов пишутся
в логи; промежуточные рассуждения модели пользователю не выводятся.
`AssistantMetadata.model_calls` теперь допускает 8; старые сценарии сохраняют
прежние runtime-лимиты. Внешние HTTP-маршруты не меняются.

**DB impact:** только SELECT по существующим таблицам/витрине. Добавлен ограниченный
пакетный reader точных снимков. Схема и исходные записи не меняются, миграция не нужна.
Мобильные сценарии не дорабатывались.

## Проверки

агентный подбор; цель сделки не должна превращаться в activity/name-фильтр.
Слишком длинный обзор получает ограниченную попытку сокращения. Статусы старых
снимков не объявляются актуальными сегодня без свежего подтверждения.
Для нуля/одного финалиста итоговая схема содержит только объяснение, без поля
сортировки. В рекомендациях сохраняются роли поставщика/покупателя и условие
без аванса; отсутствие аванса не считается гарантией последующей оплаты.
